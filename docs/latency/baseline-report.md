| 广播 emit broadcast | 0.18 ms | 0.23 ms |
| **合计 total（收到→ack前）** | **0.45 ms** | **0.55 ms** |

本机场景（30 手平均）：queue 0.06 / validate 0.01 / apply 0.02 / **persist 0.61** / state 0.01 / broadcast 0.16 / **total 0.87 ms**；P95 total 2.91 ms。

判读：

- 规则校验、引擎计算、状态构建均为微秒级；
- 唯一相对大的分项是 SQLite 同步事务（0.17–0.61 ms），但距离「秒级」差 3 个数量级；
- 因此 **B-SERVER / C-DB 类假设在本项目当前数据量下不成立**（不是两秒延迟的主因），但仍保留「同步写阻塞事件循环」的观察项。

## 5. 两秒延迟的复现

### 5.1 直接复现：polling 兜底

强制 `transports: ['polling']` 经隧道对局 8 手：

- 点击→ack：2 141 / 2 806 / 2 806 / … / 6 440 ms，**P50 2.81 s，8/8 超过 2 s**；
- 对手看到：P50 1.32 s，最大 3.67 s。

这与用户描述的「朋友走完一步之后大约要等 2 秒」高度吻合。polling 每手需要多次 HTTP 往返（POST 发送 + GET 长轮询接收），每次都要穿过「客户端 → CF 边缘 → 洛杉矶 → 家庭上行」的路径。

### 5.2 次要复现：WS 抖动

WS 路径 P50 459 ms，但 20 手里有 2 手 >1 s（1.17 s、1.20 s），插桩前一轮 16 手里有 4 手 >1 s（最大 1.48 s）。抖动来自跨太平洋链路的排队/重传，不是服务端。

### 5.3 排除项

- 服务端 total 0.45 ms，排除校验/规则/落库/序列化主因；
- ack 与对手广播几乎同时到达，排除「只广播给部分人/广播排队」；
- 本地 WS 0.79 ms，排除 Socket.IO 配置本身导致的基础延迟；
- 客户端无硬编码 500/1000/2000 ms 等待，排除前端定时器；
- 无重连、无重复连接、无 STALE_REVISION（插桩后 0 错误）。

## 6. 现有错误与异常

- 插桩前隧道首轮出现 4 次 `STALE_REVISION` / `NOT_YOUR_TURN`：探针连续走棋未等待对方广播，属于**测试脚本构造问题**，不是产品缺陷；修正探针（等待双方收到广播后再走下一手）后 0 错误。
- 隧道 HTTP 首字节单次出现 3.9 s（12 次 curl 中 1 次），说明链路存在偶发长尾。
- 服务端日志无异常；数据库无锁等待/错误。

## 7. 基线结论

1. **两秒延迟的第一主因是公网路径**：Quick Tunnel 落地洛杉矶，跨太平洋往返 400 ms 起，抖动 1–1.5 s；不是服务端、不是数据库、不是规则引擎。
2. **第二个可复现主因是 polling 兜底**：一旦 WebSocket 升级失败/被网络阻断，单手 2–6 s，正好是用户描述的体感。
3. **第三个因素是落子者自身等待一个 RTT**：没有乐观 UI，公网下自己落子也要等 400 ms+。
4. 服务端与数据库在本项目规模下性能充足；不需要为了延迟削弱校验或改技术栈。
