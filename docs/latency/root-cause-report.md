# 阶段三：两秒延迟根因报告

- 时间：2026-11-05
- 方法：真实服务端 + 两个真实 socket 客户端（`scripts/latency-probe.mjs`）+ 两个真实浏览器上下文（`scripts/latency-browser.mjs`）+ 源码逐项核对
- 原始数据：`docs/latency/raw/*.json`
- 结论：**根因不在服务端、不在数据库、不在规则引擎，而在公网链路（Cloudflare Quick Tunnel 落地洛杉矶）与 polling 兜底路径。** 落子者自身延迟已通过乐观 UI 修复（P95 2 ms）；对手可见延迟仍受公网 RTT 限制（P50 473 ms，弱网/polling 下 2 s+）。

## 0. 证据总表

| 场景 | 样本 | 点击→本机可见 | 对手可见 P50/P95 | ack P50/P95 | 服务端 total |
| --- | ---: | ---: | ---: | ---: | ---: |
| 浏览器 · 本机回环 WS | 12 | **P50 0.9 / P95 1.5 ms** | 2.3 / 4.5 ms | 4.0 / 5.7 ms | 0.36–0.40 ms |
| 浏览器 · 公网隧道 WS | 12 | **P50 1.1 / P95 2.0 ms** | 473.5 / 585.8 ms | 472.5 / 689.7 ms | 0.36–0.75 ms |
| Socket 探针 · 本机 WS | 30 | — | 0.77 / 4.53 ms | 0.79 / 4.36 ms | 0.87 ms（均值） |
| Socket 探针 · 隧道 WS | 20 | — | 416.0 / 1019.4 ms | 459.0 / 1170.7 ms | 0.45 ms（均值） |
| Socket 探针 · 隧道 **polling** | 8 | — | 1322.0 / 3665.7 ms | **2805.9 / 6439.6 ms** | 0.45 ms（均值） |

关键判读：

1. 服务端处理恒定在 **亚毫秒级**；网络 RTT 变化 1000 倍时服务端几乎不变。
2. ack 与对手可见几乎同一时刻到达（差值为抖动），不存在独立的「广播延迟」。
3. polling 路径单手 2–6 秒，**与用户描述的「约 2 秒」精确吻合**。
4. 乐观 UI 后，落子者自己的可见延迟从 470 ms 降到 1–2 ms；对手仍受物理链路限制。

## 1. A-NET：网络与连接（001–012）

### A-NET-001 是否建立长连接 —— 通过

- 复现：对局页打开后读取 `socket.io.engine.transport.name`。
- 数据：本地/隧道均为 `websocket`；连接保持，无重连。
- 结论：长连接真实存在，非「每次走棋新建连接」。

### A-NET-002 实际使用 WS 还是 polling —— **命中（第二主因）**

- 现象：某些网络/握手失败时 Socket.IO 降级为 polling，之后长时间停留。
- 复现：`node scripts/latency-probe.mjs --transport polling`。
- 数据：polling 经隧道 ack P50 **2.81 s**、P95 **6.44 s**，8/8 超过 2 s；对手可见 P50 1.32 s、最大 3.67 s。WS 同条件 P50 0.46 s。
- 根因：polling 每手需要「POST 发送 + GET 长轮询接收」多次 HTTP 往返，每次都穿越「中国 → CF 边缘 → 洛杉矶 → 家庭上行 → 服务器」。
- 影响：所有走棋/加入/选座；弱网、代理、部分移动网络更容易触发。
- 修复：① 客户端保留 polling 兜底（兼容性要求），但增加传输看门狗：检测到 polling 时最多 2 次强制重连以重新尝试 WS；② 开发者面板显式展示 transport；③ 服务端 WS 升级已确认可用。
- 验证：默认路径 100% `websocket`；看门狗逻辑已加入（强制 polling 场景下会尝试重连，见优化报告）。

### A-NET-003 服务端是否支持 WS 升级 —— 通过

- 数据：经 Cloudflare 隧道两个独立客户端均升级为 `websocket`，20 手无断线。
- 结论：服务端/隧道均支持 WS，不是「被迫 polling」的服务端原因。

### A-NET-004 是否每步走 HTTP 请求 —— 排除

- 源码：`game:move` 是 Socket.IO 事件，长连接内发送；无 per-move fetch/XHR。
- 数据：WS 下单手仅 1 次事件往返；ack 与广播同栈发出。

### A-NET-005 是否有 debounce/setTimeout 延迟 —— 排除

- 源码检索：客户端走棋路径无 `setTimeout`/debounce；唯一 `setTimeout` 是跳棋飞子 240 ms 清理，不影响逻辑。
- 数据：本机浏览器点击→本机可见 0.9 ms，排除任何定时器等待。

### A-NET-006 消息队列是否积压 —— 排除

- 数据：服务端 `queueMs` 平均 0.05 ms、P95 0.07 ms（隧道 20 手）。
- 结论：房间串行队列无积压。

### A-NET-007 是否存在重复连接 —— 排除

- 源码：`useRoom` 每个房间一个 `io()`，effect cleanup `disconnect()`；无全局单例复用导致的重复连接。
- 数据：服务端日志每客户端一条连接；无同 socket 多次 join 异常。

### A-NET-008 是否存在重复监听 —— 排除

- 源码：`socket.on('room:state'/'chat:message'/...)` 只在连接 effect 内注册一次；cleanup 断开连接并释放。
- 数据：单次广播对手只收到一次（探针按 `moves.length` 计数无重复）。

### A-NET-009 是否广播到错误房间 —— 排除

- 源码：`io.to(roomId).emit('room:state', ...)`，`roomId` 来自会话绑定。
- 数据：两个客户端均收到；无关房间未收到（探针只建一个房间，未观察到串房）。

### A-NET-010 是否服务端处理慢 —— 排除

- 数据：服务端 total 0.45 ms（隧道）/0.87 ms（本机）；分项见 B-SERVER。
- 结论：服务端不是两秒来源。

### A-NET-011 心跳/代理超时 —— 风险（未命中本次样本）

- 配置：服务端 `pingInterval 20000`、`pingTimeout 25000`；Cloudflare 对空闲 WS 有约 100 s 限制，20 s 心跳足以保活。
- 数据：本轮所有样本无主动断线/重连。
- 风险：隧道静默断线时最坏 45 s 才发现；移动网络切换时会出现一次重连+全量恢复。
- 修复建议：保持 20/25 s（过于激进会造成误判断线）；在面板展示重连次数；后续可评估 15/20 s。

### A-NET-012 弱网 —— 未测（本轮）

- 计划：Playwright CDP 限速/丢包 + 离线恢复，见多客户端测试报告；本轮尚未执行，最终报告将按实际结果标注。

## 2. B-SERVER：服务端（001–012）

| 编号 | 检查项 | 结论 | 证据 |
| --- | --- | --- | --- |
| B-SERVER-001 | 事件循环同步阻塞 | 存在但极小 | SQLite 同步事务 0.17–0.61 ms；无秒级阻塞 |
| B-SERVER-002 | 重复规则计算 | 排除 | 每手 `engine.applyMove` 一次，0.02 ms |
| B-SERVER-003 | 不必要全局遍历 | 排除 | 走棋路径只操作当前房间与引擎 |
| B-SERVER-004 | 重复 DB 查询 | 排除 | 走棋路径无 SELECT；只 INSERT + UPSERT |
| B-SERVER-005 | 每步全量序列化 | **存在，低影响** | `publicState` 含全部 moves；30 手 8.9 KB；构建 0.01 ms；Socket.IO 序列化未单独计时 |
| B-SERVER-006 | 事务锁等待 | 排除 | 单进程单写者；无 busy/locked 日志 |
| B-SERVER-007 | 同步文件 I/O | 存在但极小 | 仅 SQLite；WAL 下 0.17–0.61 ms |
| B-SERVER-008 | 聊天/统计在走棋路径 | 排除 | 聊天独立事件、独立表；无统计写 |
| B-SERVER-009 | 轮询而非推送 | 排除 | 服务端主动 `emit` 广播 |
| B-SERVER-010 | CPU 长任务/GC | 未见异常 | 本机 total P99 8.5 ms；无 GC 日志；未做堆采样 |
| B-SERVER-011 | 一个房间阻塞其他房间 | 未测（压力阶段） | 单线程；单手 0.45 ms，理论吞吐足够；需多房间并发验证 |
| B-SERVER-012 | 不必要 await 链 | 排除 | 走棋处理为同步函数，队列内无 await |

### 重点项：B-SERVER-001 / B-SERVER-005 / B-SERVER-007

- 现象：每手在广播前同步写 SQLite；广播携带全量棋谱。
- 测量：persist 0.17–0.61 ms；state 0.01 ms；broadcast 0.16–0.18 ms；total 0.45–0.87 ms。
- 根因：实现选择（一致性优先），不是延迟主因。
- 影响：单房间可忽略；高并发下同步写会串行占用事件循环，需压力测试确认上限。
- 修复方案：本轮不改变「先落库再广播」的顺序（避免丢步/不一致）；保留分项计时；如未来并发上升，再评估「先广播后异步落库 + 失败回滚」。
- 验证：分项计时已上线，压力测试见 `stress-test-report.md`。

| D-FRONT-010 | 重阴影/filter/DOM | 排除（历史已测） | 无 backdrop-filter 大面积使用；PERF-008 五棋 0 帧超 16.67 ms |

### 重点项：D-FRONT-006（STALE_REVISION）

- 现象：玩家在对手走棋广播到达前点击，服务端以 `STALE_REVISION` 拒绝，客户端提示「局面版本不一致」，该次点击不生效。
- 复现：e2e 中快速连续走棋（未等待广播）可触发；探针早期版本也触发 4 次。
- 数据：正常人类点击间隔远大于本地/隧道单程（≥400 ms），实际概率低；但在高延迟+快速点击时存在。
- 根因：客户端用本地 `stateRef.revision` 提交，服务端严格乐观锁。
- 影响：极少数快速操作需要重试；不会造成状态错乱。
- 修复方案：本轮不自动重放（避免把棋下到玩家未预期的局面）；保留「同步最新局面 + 提示重试」。后续可做「同一位置合法则自动重试一次」，需单独评审。
- 验证：e2e 仍通过；探针修正等待逻辑后 0 错误。

## 5. E-TUNNEL：公网与隧道（001–008）

### E-TUNNEL-001 服务器位置 —— 命中背景

- 服务器在本地本地家庭宽带（运营商略），非机房；上行带宽与家庭网络质量直接决定对手体感。

### E-TUNNEL-002 是否使用 Cloudflare Tunnel —— **命中（第一主因）**

- 事实：Quick Tunnel，日志 `location=lax01`，HTTP 头 `CF-Ray: ...-LAX`。
- 复现：`curl -D - https://<tunnel>/` 查看 `CF-Ray`。
- 数据：TCP 建连 0.20–0.44 s；TLS 0.42–0.74 s；首字节 1.01–1.85 s（单次 3.9 s）。
- 根因：运营商国际出口把隧道连接落到洛杉矶；每个玩家消息要跨太平洋到洛杉矶隧道入口，再回到本地家庭服务器，返回再走一遍。
- 影响：所有实时交互（走棋、加入、选座、聊天）基础 RTT 400 ms 起，抖动到 1–1.5 s。
- 修复方案（不购买付费资源）：
  1. 代码层：乐观 UI（已做，落子者 1–2 ms）；polling 看门狗（已做）；减少长局载荷（建议）。
  2. 部署层（需用户授权/操作）：家庭宽带有公网 IPv4 时做端口映射直连；有公网 IPv6 时用 IPv6 直连；或使用国内节点的免费内网穿透（需注册/实名）；或购买国内轻量服务器（任务书禁止未授权购买，故仅建议）。
  3. Cloudflare 侧：`--ha-connections 4` 实测无改善（P50 511 ms vs 459 ms，P95 941 ms vs 1171 ms，在噪声范围内），不采用。
- 验证：同机经隧道 WS P50 459 ms；本机回环 0.79 ms；差异 580 倍，且服务端耗时不变。

### E-TUNNEL-003 隧道 RTT —— 命中

- 数据：WS 单手 ack P50 459 ms、P95 1171 ms；HTTP 首字节 1.0–1.9 s。
- 结论：隧道本身是 400 ms 级通道，不是「偶发慢」。

### E-TUNNEL-004 是否频繁重连 —— 排除（本轮）

- 数据：20 手无重连；服务端日志无异常断开。
- 风险：Quick Tunnel 无 SLA，URL 随重启变化；长时间运行可能被回收。

### E-TUNNEL-005 家庭上行带宽 —— 未测

- 仅记录载荷：30 手 8.9 KB，估算 400 手约 110 KB/手广播。
- 建议：后续用长时间对局观察上行占用；当前载荷不足以解释 2 s。

### E-TUNNEL-006 直连 vs 局域网 vs 公网 —— 部分

- 本机回环：0.79 ms（代表服务端+协议下限）。
- 公网隧道：459 ms（代表跨太平洋路径）。
- 局域网/直连：**未测**（本机无全局 IPv6，路由器双重 NAT，未做端口映射）。
- 结论：差距全部来自公网路径，不是协议/服务端。

### E-TUNNEL-007 WS 是否受影响 —— 部分

- WS 可建立、可保持；但每次往返都受隧道 RTT 影响。
- polling 受影响更严重（多次往返），见 A-NET-002。

### E-TUNNEL-008 改善建议（不购买） —— 已给出

- 立即生效：乐观 UI、polling 看门狗（本轮已实现）。
- 需用户操作：公网 IP/端口映射、IPv6、国内穿透服务、或国内服务器。
- 不建议：为降低延迟关闭服务端校验、改用客户端权威、丢弃事件——违反任务书且会引入作弊/不一致。

## 6. 根因排序

1. **公网隧道路径（E-TUNNEL-002 / 003）**：跨太平洋 400 ms 基础 RTT + 1–1.5 s 抖动。解释「一直偏慢」和「偶尔很慢」。
2. **polling 兜底（A-NET-002）**：一旦触发，单手 2–6 s。解释「约两秒」的确定性复现。
3. **落子者等待一个 RTT（D-FRONT-003 缺口）**：公网下自己落子也慢；本轮乐观 UI 已修复（P95 2 ms）。
4. **长局全量载荷（B-SERVER-005）**：30 手 8.9 KB，长局可能放大抖动；非当前主因。
5. **STALE_REVISION 快速点击（D-FRONT-006）**：低概率需重试；非延迟主因。
6. **同步 SQLite（B-SERVER-001/007）**：亚毫秒级，非主因；保留观察。
7. **持久化失败一致性（C-DB-008）**：非延迟问题，但本轮已修复。
